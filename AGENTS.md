# RefundFlow — agent project charter

## Product and system goal
Build a full-stack, interview-explainable customer refund support simulation. Model several departments (for example, Support, Billing, Shipping, and Risk) with separately selectable policy collections and explicit ownership boundaries. Let an operator select departments and policy sets, submit a customer scenario, see the evidence and workflow trace, and review/approve/deny any consequential decision. Nothing may issue a real refund or contact an external party; this is a simulation until explicitly redesigned and authorized.

The product should showcase LangGraph as a real, inspectable stateful workflow: typed state, clear node/edge boundaries, specialist agent roles, bounded routing, retries/timeouts where appropriate, persistence/checkpointing, interrupt/resume human review, and an auditable event trail. Keep agent count and autonomy justified; do not add agents for decoration or create open-ended loops.

## Policy collection and changing-world RAG
- Build a sizeable *curated, department-tagged* synthetic policy collection to support the demo; do not bulk-scrape or commit raw HTML. Each policy must carry source/provenance, owner department, stable ID, version, effective-from/to, status, content hash, and license/source notes. Distinguish synthetic demo policies from external real-world references.
- Provide a controlled policy-chaos simulator: publish a new version, amend a clause, withdraw/expire a document, and schedule/effect changes deterministically for demos/tests. Expose a timeline and exactly which departments/documents changed.
- RAG is real, not mocked: implement document parsing/normalization, department/policy selection, deterministic chunking with stable chunk IDs and metadata, a real local vector/lexical retrieval path, ranking, source citations, version filters, and ingestion status. Prefer a local/offline store and replaceable interfaces; no external vector service by default.
- Incremental ingestion is mandatory: detect added/changed/removed policies by content hash/version; reprocess only affected files/chunks; preserve unchanged chunk IDs and embeddings; retire superseded chunks; make reruns idempotent; support rollback/rebuild and visible per-document provenance. Never globally invalidate all chunks for one changed file. Test unchanged-content, changed-section, deletion, version/effective-date, and failure/retry cases.
- Implement a clearly bounded prompt-cache and semantic-cache demonstration as *optional, separate layers*. Prompt-cache reuse is provider-dependent and must be described as a concept unless the selected mock/provider supports it. Semantic cache is real locally: normalized query + department + policy/version scope + model/embedding/retriever config; invalidate on relevant policy/version/config changes, never serve stale evidence, and expose hit/miss/invalidation reason. Keep freshness authoritative over cache savings.

## Architecture and engineering
- Follow a written HLD, LLD, data model, threat/safety model, ADRs, and staged roadmap. Explain component boundaries, contracts, data/control flow, failure modes, trade-offs, and chosen design patterns in interview-ready terms.
- Separate UI, API/application services, LangGraph orchestration, policy catalog, ingestion/indexing, retrievers, cache, MCP tool adapters, persistence/checkpoints, evaluation, and observability. Use dependency inversion and small interfaces; isolate infrastructure behind adapters. Frontend, HTTP, filesystem, vector store, LLM and MCP integrations should be replaceable and independently testable.
- Prefer stable existing LangChain/LangGraph middleware, checkpointers, loaders, retrievers, evaluator integrations, frontend/backend frameworks, UI components and MCP adapters when suitable. Reuse proven starter templates and existing libraries; first inventory the repo, docs and relevant maintained upstream examples to identify what already solves the requirement. Wire and configure existing pieces rather than reimplementing them; adapt only where a documented gap exists. Review license, maintenance, supply-chain/security and fit before copying/cloning any repository. Keep reused components in clear replaceable modules.
- Minimize dependencies; pin/lock versions and record why each runtime/development dependency exists. Use the existing `.venv` and installed packages. Do not reinstall/update indiscriminately. A deterministic mock LLM/provider is the only mocked core dependency for now; design a clean provider interface for a future user-supplied model. Retrieval, chunking, ingestion, vector/lexical store, MCP adapter behavior, workflow state, checkpointing, cache, API and UI must be real and testable.
- Tools must be exposed through the Model Context Protocol (MCP) interface/adapters, not ad-hoc native LangGraph tools. Keep test/local MCP servers safe and self-contained. Never connect a production/remote MCP server or add credentials without telling the owner exactly what is required and waiting for approval. When a required service/package/system dependency is absent or needs permission, stop that slice and report the exact dependency, purpose, risk/cost, install/config command, and a local alternative; continue unrelated offline work.
- Deliver a full-stack UI and API with a coherent local developer experience, accessibility, error/loading/empty states, API contract, and sample workflows. Keep frontend, backend/API, policy/RAG, LangGraph/MCP, evaluation and deployment as segregated modules with high cohesion, low coupling and explicit contracts; work across these boundaries in parallel only where the contracts are already agreed, then integrate and test end to end. Favor reuse and wiring over rewriting established frontend/backend/graph/RAG components. Add Docker/Compose deployment for reproducible local setup; document production strategy separately (secrets, health checks, non-root, persistence, backups, migrations, scaling, TLS/reverse proxy). Do not deploy or expose services publicly without authorization.
- Enterprise identity, authorization, permission-scoped RAG, async jobs, library-selection rules, and realistic security/failure acceptance are defined in [enterprise-rag-contract.md](docs/architecture/enterprise-rag-contract.md). Treat that contract as required product scope, not optional future polish. Keep identity, authorization, document policy, queue, workflow, API, UI, audit, and evaluation as independently testable modules.
- Build an enterprise simulation, not a fake demo: model tenants, users, groups, memberships, roles, permissions, document categories, scopes, and resource grants; deny by default; enforce permissions before retrieval text reaches the model. Use a maintained OIDC/authentication library and an established authorization engine behind replaceable ports; do not hand-roll JWT validation or scatter role checks. For every new dependency, compare existing compatible libraries, license, maintenance, threat model, operational burden, and local run/test fit before choosing.
- Interactive queries must be async-first and durable: separate the existing synchronous policy/index sync transaction from the not-yet-built query API; use a durable worker/queue for long-running graph jobs, async LangGraph calls, status/progress, idempotency, retries, cancellation, checkpoint/recovery and authorized HITL resume. Do not treat FastAPI `BackgroundTasks` as the only durable queue. Re-authorize at enqueue/start, retrieval/tool access, resume, and output. See the enterprise contract for the precise API/data-flow expectations.
- Simulate messy real conditions deliberately: tenant overlap, membership/ACL revocation during queued/running jobs, stale indexes/caches, duplicate/out-of-order ingestion, partial parser failures, queue redelivery/worker restart, provider timeouts, approval replay, prompt injection, and audit/logging redaction. Add deterministic tests proving cross-tenant non-interference and fail-closed behavior.
- Optional Piper TTS is a modular local adapter with graceful absence/fallback; keep model downloads optional and disclose size/licensing before fetching. TTS must not block core workflows.

## Evaluation, tests and observability
Create a reproducible evaluation harness and report metrics/artifacts, not just pass/fail. Cover retrieval (Recall@k, MRR/nDCG where labels permit, citation/faithfulness checks, freshness after changes), ingestion (incremental work counts, idempotence, rollback), agent/workflow (routing, tool selection, bounded termination, safety, human interrupt/resume), API/UI integration, cache correctness/invalidation, security and accessibility, Docker build/health. Use deterministic fixtures and labeled golden cases; separate mocked-LLM evaluation from real-provider evaluation. Never claim real LLM performance while only the mock is configured.

Implement structured, privacy-safe logs and trace/run IDs for UI/API requests, graph nodes/edges, tool/MCP calls, retrieval, ingestion/version events, cache hits/misses/invalidations, approvals, errors and evaluations. Redact customer data/secrets; provide a local observability dashboard or concise run reports. Persist decision/action audit events with actor, timestamp, input/policy versions, cited evidence, outcome and human approval. Avoid recording unnecessary PII.

## Process and durable records
- Plan before broad implementation. Stage work in `docs/ROADMAP.md`; deliver one small vertical, reviewable slice per run, and make each phase end in a locally runnable, visible product demo. Do not spend repeated cycles on design-only paperwork when a safe implementation can be made.
- For each run, update `docs/decisions/` with a versioned decision/run record: date/run ID, goal, context, alternatives, decision, consequences, touched files, dependency changes, tests/evaluation with actual output, security/artifact review, commit SHA(s), remote HEAD, blocker and next step. Keep ADRs numbered and immutable; amend by superseding, not silently rewriting history.
- Maintain `docs/architecture/HLD.md`, `docs/architecture/LLD.md`, `docs/architecture/observability.md`, `docs/evaluation/README.md`, and `docs/ROADMAP.md`. Keep documentation proportional and concise; no repetitive boilerplate.
- Use test-driven development and a pragmatic agent-native engineering loop: plan a small outcome, expose assumptions/contracts, implement a vertical slice, verify independently, document evidence and leave a clear next step. Choose top-down, bottom-up, sandwich, or contract-first testing based on risk and module boundaries; combine unit, integration, end-to-end, property/failure and evaluation tests as appropriate. Do not let Agile ceremony or a fixed test pyramid override evidence and delivery.
- The shipped application must not be hard-coded to demo fixtures or predetermined outcomes. Keep policy corpus, departments, rules, agent roles, cache behavior, evaluation datasets, tools, and model provider configurable through validated data/interfaces. Deterministic stubs/fakes are allowed only at explicit replaceable boundaries for tests or the current mock-LLM mode; label them, keep them out of the production path, and record the fidelity/limitations. RAG, ingestion, retrieval, MCP tool flow, persistence, API and UI must exercise real components in tests.
- Every test double/stub must be justified and traceable: record which boundary it replaces, why a real dependency is unavailable or unsafe in tests, what behavior it does not model, and what real integration/evaluation remains. Prefer local real implementations and in-process test servers over mocking whole subsystems.
- Use strict RED→GREEN→REFACTOR where practical: add a behavior-focused test, observe the expected failure, implement the minimum, rerun focused tests and relevant full/evaluation checks, then inspect the diff. For test levels where literal RED is inappropriate (for example, wiring an existing verified component), document the reason and verify behavior via contract/integration tests rather than inventing a failing test. Run tests in the activated `.venv` (`.venv/Scripts/python.exe` on Windows); record command and summary.
- Use exactly two long-lived branches: `main` is the stable, always-green release line; `dev` is the integration branch for active phases. Run CI on pushes to both branches and pull requests. All autonomous/cron work is confined to `dev`; never push or merge directly to `main`. A `dev` milestone may reach `main` only via a pull request after required checks pass (and owner review if configured). Do not force-push either branch. If the expected branch is missing or diverged, stop and report before rewriting history.
- Keep each commit to a logical, reviewable unit: one cohesive feature slice or tightly related set of changes, neither trivial bookkeeping nor an oversized batch. Split independent work into separate commits; keep a commit small enough to review and test, with a clear purpose and evidence. Each run may create at most two such verified commits; commit only tested/related changes, push to `dev`, then read back remote `dev` and verify it equals the pushed commit. Use concise, accurate, human-readable commit messages that describe the change; do not fake human authorship, timestamps, or provenance, and do not add AI attribution/signatures unless requested. Keep commit boundaries reviewable and grounded in actual work. Keep generated caches, venv, secrets, scraped page source, and unrelated files out of git. Maintain `.gitignore`, use secret scanning, and leave the tree clean.
- End after a bounded milestone. Never self-schedule, duplicate cron jobs, spin/retry indefinitely, or claim an unverified result. The scheduler supplies the next run. Output a short factual report with files, tests/evaluation, commit(s), verified remote head, external dependencies needing owner approval, blocker, and next roadmap item.

## Suggested phased roadmap
1. Build a visible local app shell and a trusted identity boundary (OIDC-compatible; any dev identity provider must be explicitly gated and labeled).
2. Implement tenant/user/group/membership/role/permission and document ownership/grant models; deny-by-default authorization and audit.
3. Add category/scope-aware document ingestion and permission-filtered RAG with cross-tenant non-interference tests.
4. Implement durable async query runs, queue/worker, progress/status, idempotency/retry/cancel, async LangGraph execution and durable checkpointing.
5. Add a bounded agent with least-privilege tools, human interrupt/resume, live authorization rechecks and append-only audit.
6. Exercise realistic stale/revoked permissions, indexing/queue/provider failures, prompt injection, observability, evaluation, Docker/Compose and recovery.
7. Use `docs/interviews/AI_SYSTEM_DESIGN_SCENARIOS.md` to produce interview-ready designs tied to working modules and measured evidence; keep unrelated systems as standalone exercises.
