# Decision 0020 — generation manifest schema and provenance contract

- Date/run: 2026-11-17; scheduled RefundFlow development run.
- Goal: define safe, implementable SQLite generation semantics and select the next minimal vertical slice.
- Repository state: branch `main` at `9f398f4`; worktree already contained this Decision 0020 draft plus matching roadmap/LLD edits before this run. Preserved and reviewed; no unrelated user changes overwritten.
- Skill discovery: native `skills_list`/`skill_view` unavailable; file-based catalog search selected and loaded only `test-driven-development` and `github`. Existing design contract supported by source inspection; no code slice added.
- Context: current sync atomically updates catalog, FTS and a mutable latest-outcome projection, but cannot retain immutable generations or record failed attempts. Existing catalog `record_json` is mutable lifecycle projection, not historical source authority.
- Decision: add a separate additive SQLite schema, no migration framework/dependency. `ingestion_runs(run_id PK, started_at, completed_at nullable, status CHECK running|succeeded|failed, operation CHECK sync|rollback|rebuild, recovery_of nullable FK-like run id, error_summary nullable, manifest_hash nullable)` stores immutable terminal facts; `ingestion_run_items(run_id, policy_id, source_ref, version nullable, content_hash nullable, provenance nullable, outcome CHECK added|changed|unchanged|removed|error, error_summary nullable, PK(run_id, policy_id))` stores one result per document including removals and errors. A manifest table keyed by `(run_id, policy_id)` contains every present snapshot record as canonical JSON plus its declared content hash/source identity, and is write-once; removed items remain in run items, not present manifest. `active_ingestion_generation(singleton CHECK=1, run_id)` points only to a succeeded run whose complete manifest was committed in the same transaction as catalog/FTS reconciliation and status projection. Preserve the existing latest sync outcome projection for compatibility until consumers migrate; it is not history. The first implementation slice should add schema and read-only status/history projection only, then sync recording/pointer activation as a separate tested slice. Failed-run recording is a separate short transaction after failed sync rollback, best effort; if SQLite cannot persist it, surface explicit unrecorded failure.
- Invariants: terminal run/item/manifest rows are append-only (enforce in application and test; triggers may be added if they do not complicate migrations); manifest hash is deterministic over sorted policy IDs and canonical record bytes; at most one active pointer; pointer references succeeded complete manifest only; no active pointer change on failed sync; each run's document outcomes are explicit and removed documents are visible; source records are captured before writes and source mutation is checked before activation; no Chroma or network involvement.
- State transitions: create `running` row before work; success updates it once to `succeeded` and switches pointer within the existing catalog/index transaction; failure rolls back that transaction then records `failed` and item errors independently where possible. No `rolled_back` mutation on historical rows: a later compensating run references its target via `recovery_of` and only after success is the prior generation considered inactive.
- Failure/recovery: preserve the previous active generation and catalog/FTS snapshot on any failed mutation. If separate failure recording fails, return/raise original sync error annotated with durable-recording failure; never present an unrecorded run as persisted. Incomplete `running` rows found after process interruption remain explicitly interrupted/unknown, are not active, and require operator retry; do not silently mark failed at startup. No destructive cleanup or automatic repair.
- Acceptance criteria: schema initialization is idempotent against existing databases and legacy status table; schema tests verify constraints and reopen persistence; status/history reads deterministic ordering and includes removed/error items; no sync behavior changes in this schema/read-model slice; subsequent sync slice verifies atomic pointer activation and injected transaction rollback, with failed-run persistence isolated from active projection. Rollback/rebuild remain later work from canonical manifest bytes. Chroma remains absent/gated.
- Alternatives: retrofit catalog record_json as history (rejected: lifecycle mutations erase prior values); make filesystem the rollback authority (rejected: mutable/disappearing source); include all migration, sync, rollback and rebuild in one change (rejected: oversized and failure-prone); install external migration library (rejected: stdlib SQLite suffices for current schema size).
