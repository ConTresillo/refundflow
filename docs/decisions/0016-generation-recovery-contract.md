# Decision 0016 — source generation recovery and operator status

- Date/run: 2026-11-17; scheduled RefundFlow development run.
- Goal: define safe source-ingestion generation, rollback/rebuild, and per-document status semantics before implementation.
- Context: Decision 0015 made catalog lifecycle and SQLite FTS synchronization atomic but did not persist ingestion-run history, a restorable manifest, or operator-facing provenance status. SQLite is canonical; Chroma remains security-gated and is not present.
- Decision: adopt the contract in `docs/architecture/LLD.md` under “Source-generation recovery and operator status (decision 0016)”. A successful generation is an immutable, complete source manifest plus item outcomes; failed work cannot become active. Recovery is compensating, append-only, and transactional across SQLite catalog and FTS. Rebuild is derived-data reconstruction from hash-verified canonical records; rollback re-applies a previous successful manifest as a new generation. Changes to the source tree during sync abort rather than publish a mixed snapshot. SQLite-only guarantees apply; future vector synchronization must expose lag and be repairable without overriding canonical freshness.
- Alternatives: mutate/delete history to restore (rejected: destroys auditability); keep only latest state and re-read files for rollback (rejected: files can change/disappear); stage SQLite and Chroma as if cross-store atomic (rejected: no distributed transaction and Chroma is gated); keep no run status (rejected: operator cannot distinguish failure from current state).
- Invariants: one active successful generation pointer; source/run/item records immutable after terminal status; a failed run leaves the pointer and active catalog/index snapshot unchanged; each restored generation links its source generation; hash validation precedes activation; item provenance/status is queryable per document; rollback does not delete events; repeated application is idempotent; no Chroma dependency or external effects.
- State transitions: run `running -> succeeded|failed`; recovery of a prior snapshot creates a new `running` run then `succeeded` with `recovery_of` reference and operation `rollback|rebuild`. `rolled_back` describes a prior generation only when a later compensating generation has committed; it never erases the prior run or event history. Item outcomes: `added|changed|unchanged|removed|error`.
- Failure/recovery: parse/hash/source mutation/SQLite failure records a failed run where durable recording is possible and retains the previous active generation. If SQLite itself is unavailable, report the run as unrecorded failure to the caller; do not imply persisted status. A manifest mismatch aborts and requires a fresh sync. Rebuild verifies every source record/hash before transaction commit. Chroma stays out of the first implementation; future adapter errors are visible as derived-index lag and repaired from SQLite.
- Acceptance criteria for implementation: migrations/schema for immutable run/item/manifest and active pointer; status query reports run and per-policy provenance/outcome; success switches pointer atomically; injected failure and changed-source tests prove no active-state change; rollback restores prior catalog/FTS and appends rather than deletes events; rebuild is idempotent; corrupt/missing source rejects safely; full suite, lint, compile and dependency checks pass; Chroma remains absent/gated.
