# Decision 0038 — Transactional IAM authorization revision

- Date: 2026-11-21. Goal: establish a revision primitive for P1's live authorization snapshot refresh.
- Context: P0 clean Windows lock and exact-SHA CI completed (decision 0037). The next roadmap item is P1a; SQLite membership writes are already transactional and audited, but there was no revision signal for consumers to distinguish stale authorization snapshots.
- Decision: add a singleton SQLite revision row initialized to zero. Principal replacement and successful deletion increment it in the same transaction as state and audit changes. Deleting a missing principal is a no-op and does not increment. Expose a read method for consumers. This is groundwork only: tenant-role/doc snapshots and a consistent combined snapshot are still incomplete.
- Alternatives: infer revision from audit sequence (couples callers to audit storage and cannot express the snapshot contract clearly); process-local counters (lost across restart and not cross-worker safe); rebuild authorization ad hoc (stale-cache risk).
- Files: `app/iam_store.py`, `tests/test_iam_store.py`, `docs/ROADMAP.md`, this record.
- Test-first evidence: added regression, ran it before implementation; it passed immediately because the store already exposed a semantically similar counter in the current workspace. Therefore a RED failure was not observed; no claim of TDD RED. The existing implementation additions were then run against the test and verified.
